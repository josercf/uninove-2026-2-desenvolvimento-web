O que é uma API e o que REST acrescenta [1]

API é o contrato pelo qual um programa fala com outro. REST é um estilo de organizar esse contrato usando o que o HTTP já tinha: endereço, verbo e código de status.

O recurso é um substantivo

Consulta, paciente, médico. A URL nomeia a coisa, no plural, e nunca a ação: api/consultas.

O verbo diz a operação

O mesmo endereço serve para ler, criar, alterar e remover. O que muda é o método HTTP da requisição.

Sem estado entre chamadas

Cada requisição carrega tudo o que o servidor precisa. Ele não guarda memória de quem chamou antes.

GET    /api/consultas              certo: o recurso no plural
GET    /api/consultas/42           certo: um item do recurso, pelo identificador
GET    /api/listarConsultas        errado: o verbo virou pedaço da URL
POST   /api/consultas/excluir/42   errado: DELETE já existe para isso

Um endereço, cinco verbos [2]

Na Aula 02 você viu GET e POST em formulários. A API usa a família inteira, e cada verbo carrega uma promessa sobre o que acontece com o recurso.

VerboIntençãoSobre qual endereçoRepetir a mesma chamada
GETler, sem alterar nadaa coleção ou um itemnão muda nada, à vontade
POSTcriar um item novoa coleçãocria outro; cuidado com o clique duplo
PUTsubstituir o item inteiroum itemo resultado é sempre o mesmo
PATCHalterar só uma parteum itemo resultado é sempre o mesmo
DELETEremoverum itemda segunda vez, já não existe
Takeaway

Se a sua URL tem verbo dentro, a modelagem está errada. O verbo viaja no método HTTP, não no caminho.

As famílias da Aula 02, agora sobre recursos [2]

As quatro famílias você já conhece: 2xx deu certo, 3xx foi para outro lugar, 4xx o cliente errou, 5xx o servidor errou. O que muda é que agora quem lê o número é um programa, e ele decide o que fazer só por ele.

O Controller de API: três atributos e nenhuma View [3]

[ApiController]              // liga o comportamento de API neste Controller
[Route("api/consultas")]     // o recurso, no plural, sem verbo nenhum
[Authorize]                  // herda o cookie de autenticação da Aula 15
public class ConsultasApiController : ControllerBase
{
    private readonly ClinicaContext _context;

    public ConsultasApiController(ClinicaContext context) => _context = context;
}
  • [ApiController] transforma modelo inválido em 400 sozinho, antes da action rodar, e lê o corpo JSON sem precisar de [FromBody].
  • ControllerBase é o Controller sem o que só serve a HTML: nada de View, nada de TempData.

Sobre a rota: a convenção é [Route("api/[controller]")], com o token virando o nome da classe sem o sufixo Controller. Aqui ele daria api/consultasapi, porque a classe se chama ConsultasApiController para não colidir com o Controller MVC. Quem manda é o recurso: fixamos api/consultas.

Por que não devolver a entidade do EF Core

É tentador escrever return Ok(consulta) e ir para casa. O problema não aparece hoje: aparece quando a sua tabela mudar e o sistema do parceiro parar sem que ninguém tenha mexido nele.

Devolvendo a entidade

  • O contrato vira cópia da tabela, e os tipos são os do banco: Horario sai como "14:30:00".
  • Na Aula 17, a navegação entre entidades gera ciclos na serialização.

Devolvendo um DTO

  • Você escolhe, campo a campo, o que sai, com que nome e em que formato: "14:30".
  • O DTO de entrada define o que a API aceita, e nada além disso.
public record ConsultaResponse(int Id, int PacienteId, int MedicoId,   // saída
                               string Data, string Horario, string? Observacoes);
public class ConsultaRequest   // entrada: sem Id, porque quem gera o Id é o banco
{
    [Required] public int PacienteId { get; set; }
    [Required] public int MedicoId { get; set; }
    [Required] public DateTime Data { get; set; }          // "2026-11-25"
    [Required] public string Horario { get; set; } = "";   // "14:30"
}

Cada status tem um método [3]

A action é declarada como ActionResult<T>: ou ela devolve o objeto T, ou devolve um resultado de status. Um tipo só cobre os dois caminhos.

O que você quer dizerO que você escreveStatus
aqui está o recursoreturn Ok(dto);200
criei, e ele mora neste endereçoreturn CreatedAtAction(...);201
feito, e não há o que devolverreturn NoContent();204
o que você mandou não servereturn BadRequest("motivo");400
esse recurso não existereturn NotFound();404

O 400 de campo obrigatório faltando você não escreve: com [ApiController], a validação das Data Annotations roda antes da action e a requisição inválida nem chega ao seu código. O BadRequest que você escreve à mão é para a regra de negócio, como um MedicoId que não existe no banco.

O 201 e o cabeçalho que quase todo mundo esquece [2]

O 201 não é um 200 mais bonito. Ele diz duas coisas que o 200 não diz: que alguma coisa passou a existir, e em que endereço ela mora.

Takeaway

CreatedAtAction monta o Location a partir da action que lê o item. Se você renomear essa action, o nameof acompanha e o cabeçalho continua certo.

A agenda que trancamos na semana passada continua trancada

Seria estranho proteger a agenda na Aula 15 e, sete dias depois, publicar GET api/consultas aberto para a internet inteira. A API é a mesma aplicação: o [Authorize] no Controller reaproveita o cookie do Identity.

// Program.cs: quem chama /api sem cookie recebe 401, e não a tela de login em HTML
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Events.OnRedirectToLogin = ctx =>
    {
        if (ctx.Request.Path.StartsWithSegments("/api")) ctx.Response.StatusCode = 401;
        else ctx.Response.Redirect(ctx.RedirectUri);
        return Task.CompletedTask;
    };
});

Com honestidade: cookie foi feito para navegador, e o navegador o reenvia sozinho. Um sistema parceiro não tem navegador, e teria de guardar o nosso cookie na mão. Integração de verdade usa token, com padrões como OAuth 2.0 e JWT. Não está na ementa da disciplina e não entra hoje: fica como estudo adiante.

Como se testa o que não tem tela [4]

A barra de endereços do navegador só faz GET. Para os outros quatro verbos você precisa de uma ferramenta: um arquivo .http no próprio projeto, o Postman ou uma interface de Swagger.

@host = https://localhost:7145
@cookie = .AspNetCore.Identity.Application=COLE_AQUI_O_SEU

### agenda de um dia, de um médico
GET {{host}}/api/consultas?data=2026-11-25&medicoId=3
Cookie: {{cookie}}

### agendar uma consulta nova
POST {{host}}/api/consultas
Content-Type: application/json
Cookie: {{cookie}}

{ "pacienteId": 1, "medicoId": 3, "data": "2026-11-25", "horario": "14:30" }

A porta 7145 é exemplo: use a porta que o seu terminal imprimiu. O cookie sai do DevTools, aba Application, depois do login. Copiar cookie à mão é chato: é a limitação do slide anterior, na prática.

Quiz de fixação

Qual código de status uma API REST deve devolver ao criar um recurso com sucesso?
  • A 200 OK sempre, porque a requisição foi processada com sucesso e o corpo já traz o recurso criado.
  • B 204 No Content, porque o cliente conhece os dados que enviou e o corpo da resposta se torna dispensável.
  • C201 Created, com o cabeçalho Location apontando para o endereço do recurso recém-criado.
  • D 302 Found, redirecionando o cliente para o endereço em que o recurso criado pode ser consultado.

Em Models/Dtos/

private static ConsultaResponse ParaResposta(Consulta c) => new(
    c.Id, c.PacienteId, c.MedicoId,
    c.Data.ToString("yyyy-MM-dd"),

Laboratório, passo 3 de 6: GET api/consultas

A listagem, com filtro por data e por médico

  1. Os dois filtros são opcionais: sem nenhum deles, a resposta é a agenda inteira.
  2. Monte a consulta condicionalmente e só vá ao banco no ToListAsync.
  3. Lista vazia é 200 com [] no corpo, nunca 404: a coleção existe, e está vazia.
[HttpGet]
public async Task<ActionResult<IEnumerable<ConsultaResponse>>> GetConsultas(
    [FromQuery] DateTime? data, [FromQuery] int? medicoId)
{
    var query = _context.Consultas.AsQueryable();
    if (data is not null) query = query.Where(c => c.Data == data.Value.Date);
    if (medicoId is not null) query = query.Where(c => c.MedicoId == medicoId);

    var consultas = await query.OrderBy(c => c.Data).ThenBy(c => c.Horario).ToListAsync();
    return Ok(consultas.Select(ParaResposta));
}

Laboratório, passo 4 de 6: GET api/consultas/{id}

Uma consulta específica, e o 404 honesto

  1. A restrição {id:int} na rota descarta sozinha um /api/consultas/abc.
  2. Registro inexistente devolve NotFound(), e não uma resposta vazia com 200.
  3. Esta é a action que o CreatedAtAction do passo 5 vai apontar: guarde o nome dela.
[HttpGet("{id:int}")]
public async Task<ActionResult<ConsultaResponse>> GetConsulta(int id)
{
    var consulta = await _context.Consultas.FindAsync(id);
    if (consulta is null) return NotFound();

    return Ok(ParaResposta(consulta));
}

Laboratório, passo 5 de 6: POST api/consultas

Criar, agora sozinho

  1. Converta o Horario de texto para TimeSpan com TryParse, devolvendo BadRequest se não der.
  2. Confira se o PacienteId e o MedicoId existem no banco: se não existirem, é 400, não 500.
  3. Grave e devolva 201 com CreatedAtAction, apontando para a action do passo 4.
[HttpPost]
public async Task<ActionResult<ConsultaResponse>> PostConsulta(ConsultaRequest dto)
{
    // ... validações e montagem da entidade Consulta
    _context.Consultas.Add(consulta);
    await _context.SaveChangesAsync();

    var resposta = ParaResposta(consulta);
    return CreatedAtAction(nameof(GetConsulta), new { id = consulta.Id }, resposta);
}

Laboratório, passo 6 de 6: PUT, DELETE e o teste

Remarcar, cancelar e provar que funciona

  1. PUT api/consultas/{id} substitui os dados da consulta e devolve 204; id inexistente é 404.
  2. DELETE api/consultas/{id} remove e devolve 204; id inexistente é 404.
  3. Registre as cinco chamadas em ClinicaVida.http, na raiz do projeto, e execute todas.
  4. Documente a tabela de endpoints no README.md do seu fork.
[HttpDelete("{id:int}")]
public async Task<IActionResult> DeleteConsulta(int id)
{
    var consulta = await _context.Consultas.FindAsync(id);
    if (consulta is null) return NotFound();
    _context.Consultas.Remove(consulta);
    await _context.SaveChangesAsync();
    return NoContent();
}

O que fica desta aula

Uma aula atrás a Clínica Vida+ só sabia conversar com pessoas. Agora ela conversa com outros sistemas, e o que garante isso não é o JSON: é o contrato.

O recurso manda na URL

Duas rotas, api/consultas e api/consultas/{id}, dão conta das cinco operações. O verbo vai no método HTTP.

O status é resposta, não enfeite

200, 201 com Location, 204, 400, 401 e 404. Quem lê o número é um programa, e ele decide por ele.

O DTO protege as duas pontas

O contrato da API não é a sua tabela. Mudar o banco por dentro não pode quebrar quem consome de fora.

Prévia da Aula 17: a resposta que a sua API devolve hoje traz pacienteId: 1 e medicoId: 3. O laboratório parceiro quer o nome do paciente e a especialidade do médico, e você não tem como buscá-los sem sair do Consultas. Na próxima aula as quatro entidades do case se ligam de verdade, com chaves estrangeiras, propriedades de navegação e Include.
