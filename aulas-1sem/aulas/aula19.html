De onde viemos: a aplicação pronta, e presa

Na Aula 18 você entregou o _Layout.cshtml e as Partial Views com Bootstrap 5 na paleta da clínica, com todas as telas responsivas. A aplicação está pronta. Só que ela roda em um lugar só.

O que já existe

CRUD de pacientes, agendamento com regra de conflito, agenda do dia, login com perfis, API REST e layout unificado. Dezoito encontros de trabalho.

O problema de hoje

Tudo isso responde em https://localhost: mais a porta que o seu terminal sorteou. Ninguém fora da sua máquina alcança esse endereço, nem a recepção da clínica, nem o professor.

O que muda hoje

A aplicação e o banco viram contêineres, sobem no GitHub Codespaces e ganham um endereço https:// que qualquer celular abre.

Takeaway

Software que não está publicado não existe para quem precisa dele. Publicar não é um detalhe do fim do projeto: é o que transforma código em serviço.

Desenvolvimento contra produção [1]

É a mesma aplicação e o mesmo código compilado. O que muda é o ambiente, e o ambiente muda o comportamento em pontos que importam. O Program.cs decide pelo ASPNETCORE_ENVIRONMENT.

Development, a sua máquina

  • Página de exceção detalhada, com a pilha de chamadas e o trecho do código na tela
  • Dados de teste, log em Information
  • Erro na tela é ajuda: quem lê é você

Production, o mundo

  • Página de erro amigável, sem uma linha de código exposta
  • Dados reais, log em Warning
  • Erro na tela é vazamento: quem lê é qualquer um
if (app.Environment.IsDevelopment())
    app.UseDeveloperExceptionPage();
else
{
    app.UseExceptionHandler("/Home/Error");
    app.UseHsts();
}

ASPNETCORE_ENVIRONMENT e a cascata [1]

A configuração do ASP.NET Core é lida em camadas, de baixo para cima. Quem é lido por último vence, e é isso que permite publicar sem editar arquivo nenhum.

Takeaway

Publicar não é editar arquivo. É definir a variável certa no ambiente certo, e deixar a camada mais alta sobrescrever o que está versionado.

Segredo não mora no repositório [2]

Uma chave aninhada do appsettings.json vira variável de ambiente trocando os dois-pontos por duplo sublinhado. O nome da variável é a única coisa que você precisa acertar.

Chave na configuraçãoVariável de ambiente equivalente
ConnectionStrings:DefaultConnectionConnectionStrings__DefaultConnection
Logging:LogLevel:DefaultLogging__LogLevel__Default
SeedRecepcao:Senha, da Aula 15SeedRecepcao__Senha

Dois-pontos não é caractere válido em nome de variável em todos os sistemas. O duplo sublinhado é a convenção oficial de escape, e o ASP.NET Core o converte de volta ao carregar.

Em desenvolvimento: dotnet user-secrets set guarda o valor no seu perfil de usuário, fora da pasta do projeto, e por isso ele nunca entra em um git add distraído.

O pacote de publicação: dotnet publish [3]

Publicar é gerar uma pasta autocontida: o que ela tem dentro é tudo o que o servidor precisa, e nada mais. Código-fonte não vai junto.

# Compila em Release e escreve o pacote em ./publicado
dotnet publish ClinicaVida.Web/ClinicaVida.Web.csproj -c Release -o ./publicado

# A aplicação publicada roda sem o SDK, só com o runtime
cd publicado
dotnet ClinicaVida.Web.dll

O que a pasta tem

  • ClinicaVida.Web.dll e as bibliotecas do NuGet
  • wwwroot/, com o CSS e o JavaScript
  • appsettings.json e o do ambiente
  • *.runtimeconfig.json e *.deps.json

Debug contra Release

  • Debug traz símbolos e desliga otimizações
  • Release otimiza e é o que vai para produção
  • dotnet publish já usa Release por padrão desde o .NET 8, mas escreva o -c Release assim mesmo

Onde publicar uma aplicação com banco

Uma aplicação ASP.NET Core com MySQL precisa de dois serviços no ar ao mesmo tempo. As opções mudam em custo, em esforço e no que a camada gratuita permite.

OpçãoCustoO que pesa
Servidor próprio, ou VPSMensal, em dólarVocê cuida do sistema, do banco, do certificado e das atualizações
Nuvem gerenciadaCamada gratuita curtaCartão de crédito exigido no cadastro, mesmo no plano gratuito
Plataforma de contêinerGratuito com limitesBanco costuma ser cobrado à parte, e a aplicação hiberna sem uso
Docker no GitHub CodespacesCota gratuita da contaAplicação e banco no mesmo lugar, com HTTPS pronto e sem cartão

Nesta disciplina o provedor é o GitHub Codespaces, com cota mensal gratuita de horas na conta pessoal. Containerizar e configurar por variável de ambiente vale igual em qualquer nuvem.

A imagem multi-stage: compilar em uma, entregar outra [3]

Compilar exige o SDK inteiro. Executar exige só o runtime. O Docker deixa você usar os dois e mandar para o servidor apenas o segundo.

Takeaway

Multi-stage não é capricho: é o que impede o compilador, o código-fonte e o histórico do Git de viajarem para o servidor junto com a aplicação.

19 A imagem multi-stage
11

O Dockerfile da Clínica Vida+ [3]

# Etapa 1: build. O SDK completo compila e publica.
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY ClinicaVida.Web/*.csproj ClinicaVida.Web/
RUN dotnet restore ClinicaVida.Web/ClinicaVida.Web.csproj
COPY . .
RUN dotnet publish ClinicaVida.Web/ClinicaVida.Web.csproj -c Release -o /app/publish

# Etapa 2: runtime. Só o necessário para executar.
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app/publish .
EXPOSE 8080
ENTRYPOINT ["dotnet", "ClinicaVida.Web.dll"]

Por que o .csproj é copiado sozinho antes do resto? Cada linha vira uma camada em cache. Enquanto você não mexer nas dependências, o restore não roda de novo, e o build de uma alteração de View leva segundos em vez de minutos.

Dentro do compose, o host é db, não localhost

Cada contêiner tem a própria rede. localhost, dentro do contêiner da aplicação, é o próprio contêiner da aplicação: não existe MySQL ali. O compose publica o nome do serviço como nome de host.

Errado, e é o erro número um

server=localhost;database=clinicavida

Resultado: Unable to connect to any of the specified MySQL hosts, ou conexão recusada na 3306.

Certo

server=db;database=clinicavida

db é o nome do serviço no compose.yaml, e o compose resolve esse nome dentro da rede.

# O db precisa estar aceitando conexão antes de o web tentar
db:
  healthcheck:
    test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-u", "root", "-p$$MYSQL_ROOT_PASSWORD"]
    interval: 10s
    retries: 12
    start_period: 30s

De onde vem a URL: a porta encaminhada [5]

O codespace roda em um computador do GitHub. Quando um processo começa a escutar em uma porta, o GitHub cria um endereço para ela. Quem decide se esse endereço é acessível é você.

docker compose up
→
porta 8080 detectada
→
aba PORTS, Public
→
URL para a turma

Private, o padrão

Só você abre. Qualquer outra pessoa, inclusive o professor, recebe 401 ou a tela de login do GitHub. É o esquecimento mais comum da aula.

Public

Qualquer um com o endereço abre, sem conta no GitHub. É o que o entregável de hoje e a apresentação da Aula 20 exigem.

Takeaway

Publicar aqui é encaminhar uma porta e marcá-la como pública. Se a URL só abre para você, o deploy não aconteceu.

O HTTPS vem do proxy, e a URL tem prazo [5]

Quem termina o TLS é o GitHub

O contêiner serve HTTP puro na 8080; o certificado é do proxy do GitHub. Por isso UseHttpsRedirection dentro do contêiner só produz redirecionamento para uma porta que não existe.

Para o login da Aula 15 continuar funcionando, a aplicação precisa confiar no cabeçalho X-Forwarded-Proto com UseForwardedHeaders. Sem isso, ela se acha em HTTP e descarta o cookie seguro.

A limitação, dita com todas as letras

A URL existe enquanto o codespace está rodando. Depois de um tempo sem uso ele hiberna, e o endereço para de responder até você iniciá-lo de novo.

Isso não é defeito do material nem erro seu: é como o Codespaces funciona, e é o preço de um deploy sem cartão de crédito.

Combinado para a Aula 20: a apresentação do projeto final exige a URL respondendo. Inicie o seu codespace, rode o docker compose up e confira a porta pública antes de entrar na sala, não na hora de apresentar.

Exercício do Ciclo 2: o seu checklist

No README.md do seu fork, 8 minutos

  1. Crie a seção Publicação e escreva o checklist com as suas palavras, um item por linha, em caixas de marcação do Markdown.
  2. Ao lado de cada item, escreva como você vai conferir aquilo, e não apenas o que é.
  3. Acrescente dois itens que só existem no seu projeto, por causa de algo que você fez diferente nas aulas anteriores.

Critério: um colega precisa conseguir publicar o seu projeto lendo apenas esse trecho do README.md, sem perguntar nada a você.

Quiz de fixação

Onde deve ficar a senha do banco de dados de produção?
  • ANo appsettings.json, que é versionado junto com o código e por isso acompanha cada publicação.
  • BNo README.md, junto das instruções de instalação, para quem precisar publicar a aplicação outra vez.
  • C Fora do repositório, em variável de ambiente ou no serviço de segredos do provedor de hospedagem.
  • D Em um comentário ao lado da connection string, separado do restante da configuração da aplicação.

Laboratório, passo 5: migrations, seed e o proxy

Ciclo 4, sozinho, 12 minutos

  1. Acrescente o bloco de Migrate() e de semeadura no Program.cs, antes do app.Run().
  2. Configure o UseForwardedHeaders, senão o login cai atrás do proxy do GitHub.
  3. Suba de novo com docker compose up --build e confira no log que a migration foi aplicada.
  4. Confirme no banco do contêiner que as tabelas e as especialidades estão lá.
docker compose exec db mysql -u clinica -p clinicavida -e "SHOW TABLES;"

Dois detalhes que derrubam a aplicação no arranque: o UseHttpsRedirection precisa ficar só em desenvolvimento, e a senha do usuário inicial da Aula 15 precisa chegar como SeedRecepcao__Senha, pelo .env, porque dentro do contêiner não existe user-secrets.

Laboratório, passo 6: porta pública e teste real

Ciclo 4, sozinho, 13 minutos

  1. Na aba PORTS, clique com o botão direito na porta 8080 e marque Port Visibility: Public.
  2. Abra a URL em uma janela anônima: se pedir login do GitHub, a porta ainda está privada.
  3. Pela URL, e não por localhost, teste cadastro de paciente, agendamento, login e a API de consultas.
  4. Registre no README.md a URL pública e as instruções de publicação, e envie o commit.

Teste do colega: mande a sua URL para quem está ao lado e peça que ele abra no celular dele, na rede de dados. Se abrir na sua máquina mas não na dele, ou a porta está privada, ou o codespace parou.

Entregável de hoje, commit e push

Aplicação publicada, com URL acessível pela internet, banco de produção configurado e a URL registrada no README.md.

Cinco arquivos novos

Dockerfile, compose.yaml, .dockerignore, o devcontainer.json e a seção de publicação do README.md.

Um arquivo que não é entregue

O .env. Ele fica na sua máquina e no codespace, e nunca no repositório. Se ele aparecer no git status, algo está errado.

Uma URL que responde

Aberta em janela anônima, sem pedir login do GitHub, com cadastro, agendamento, login e API funcionando.

git add Dockerfile compose.yaml .dockerignore .devcontainer/ .gitignore README.md Program.cs
git commit -m "feat: publicacao da Clinica Vida com Docker e Codespaces"
