02 O caminho de uma requisição

As quatro camadas do modelo TCP/IP [2]

Cada camada resolve um problema e não precisa saber como a de baixo trabalha.

No agendamento: HTTP é aplicação; TCP cuida da porta; IP, do endereço; wi-fi, do sinal.

Takeaway

Trocar o wi-fi por cabo não muda uma linha do seu HTML: é para isso que servem as camadas.

02 Camadas do modelo TCP/IP
6

Endereço IP, porta e a escolha entre TCP e UDP [2]

O IP identifica a máquina; a porta identifica o programa que atende dentro dela. É por isso que o mesmo servidor da Clínica Vida+ pode responder o site na porta 443 e o MySQL na 3306.

Endereço IP

O número da máquina na rede, como 203.0.113.42 em IPv4. É o endereço da rua; sem ele não há como entregar nada.

Porta

O apartamento dentro do prédio. 80 para HTTP, 443 para HTTPS, 3306 para MySQL, 5001 para o ASP.NET local.

Socket

IP mais porta, dos dois lados. É esse par que identifica de forma única cada conversa aberta no seu computador.

TCP, o que a web usa

Abre conexão com aperto de mão, numera cada pedaço, confirma o recebimento e reenvia o que se perdeu. Custa alguns milissegundos a mais e entrega a página inteira e na ordem certa.

UDP, quando velocidade vale mais

Dispara sem conexão e sem confirmação. Serve para voz, vídeo ao vivo e para a própria consulta de DNS. Um quadro perdido na chamada passa; meio HTML não passa.

Takeaway

A web escolheu TCP porque HTML, CSS e JavaScript não toleram byte faltando. Confiabilidade vale mais que latência quando o resultado precisa chegar completo.

Demonstração ao vivo e exercício do Ciclo 1

Três comandos mostram, no terminal, o que os dois slides anteriores descreveram em desenho. Acompanhe na sua máquina.

ipconfig            # Windows: o IP da sua máquina, a máscara e o gateway
ifconfig            # Linux e macOS: o mesmo, com outro nome

ping uni9.br        # a máquina responde? em quantos milissegundos?

tracert uni9.br     # Windows: cada roteador entre você e o destino

O que observar: o ping devolve o IP por trás do nome, prova de que o DNS já respondeu. O traceroute mostra que a sua requisição atravessa uma dezena de roteadores, cada um deles uma decisão da camada de internet.

02 Demonstração e exercício do Ciclo 1

DNS: o nome vira endereço IP [1]

Nenhum roteador da internet entende clinicavidamais.com.br. Ele só sabe encaminhar pacotes para endereços IP. O DNS é a agenda telefônica distribuída que faz essa tradução, antes de qualquer requisição HTTP existir.

Cache: guardada a resposta pelo prazo do TTL, os passos 2, 3 e 4 são pulados.

Takeaway

O DNS acontece antes de qualquer HTTP. Se ele falha, o navegador nem chega a abrir conexão.

02 DNS e resolução de nomes
9

Anatomia de uma URL [3]

A URL não é um texto solto: é um endereço com seis partes, e cada uma delas é lida por um componente diferente do caminho que acabamos de percorrer.

Quem lê o quê: o host vai ao DNS; a porta, ao servidor; o caminho, ao HTTP.

Takeaway

O fragmento nunca sai do navegador: o que o servidor precisa saber vai no caminho ou na query.

02 Anatomia de uma URL
10

Uma requisição e uma resposta HTTP, linha a linha [3]

HTTP é texto. Toda a conversa entre o navegador do paciente e o servidor da clínica cabe em duas mensagens que você consegue ler.

O navegador pede

GET /consultas/agendar?medico=12 HTTP/1.1
Host: clinicavidamais.com.br
User-Agent: Mozilla/5.0 (Windows NT 10.0)
Accept: text/html
Cookie: sessao=8f3a91c2

O servidor responde

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 5124
Date: Wed, 12 Aug 2026 22:41:03 GMT

<!DOCTYPE html> ... a agenda do dia

GET, para buscar

Os dados vão na query string, à vista na URL, no histórico e nos logs. Serve para consultar a agenda, nunca para enviar o CPF do paciente.

POST, para enviar

Os dados vão no corpo da mensagem, fora da URL. É o método do formulário de agendamento que vamos construir na Aula 05.

Takeaway

A linha em branco separa os cabeçalhos do corpo. Tudo antes dela é sobre a mensagem; tudo depois é a mensagem.

02 Requisição e resposta HTTP
11

Códigos de status, por família [3]

O primeiro dígito já diz de quem é o problema. Decore as cinco famílias e você lê qualquer código sem consultar tabela.

FamíliaO que significaExemplo na Clínica Vida+
1xxInformativo, siga em frente101: troca de protocolo, raro no dia a dia
2xxDeu certo200 OK: a agenda do dia foi devolvida
3xxMudou de lugar301: /agenda agora é /consultas
4xxO erro está no pedido404: o médico 999 não existe. 401: sem login
5xxO erro está no servidor500: falhou ao gravar a consulta no banco
Takeaway

4xx é culpa de quem pediu, 5xx é culpa de quem respondeu. Essa única distinção resolve metade das discussões entre front-end e back-end.

No laboratório de hoje você vê esses códigos ao vivo, um por linha da aba Network do DevTools.

02 Códigos de status HTTP
12

O que o HTTPS acrescenta ao HTTP [4]

HTTPS é o mesmo HTTP dentro de um túnel TLS. O formulário de agendamento carrega CPF, telefone e data de nascimento: dado pessoal sensível, que jamais pode trafegar em texto puro.

Takeaway

O TLS entrega três coisas: sigilo do conteúdo, integridade contra alteração no caminho e a prova, pelo certificado, de que o servidor é mesmo quem diz ser.

02 Demonstração e exercício do Ciclo 2

Quiz de fixação

Qual é o papel do DNS em uma requisição web?
  • A Criptografar o tráfego entre o navegador e o servidor, para que ninguém no caminho consiga ler o conteúdo.
  • B Comprimir o HTML antes de enviá-lo ao navegador, para reduzir o tempo de carregamento da página.
  • C Traduzir o nome do domínio no endereço IP do servidor, para que a conexão possa ser estabelecida.
  • D Guardar os cookies do usuário entre uma visita e outra, para que o servidor reconheça quem está acessando.

Laboratório, passo 1 de 4: investigar o DNS

A missão dos próximos 60 minutos é documentar a arquitetura pela qual o site da Clínica Vida+ vai passar a operar. Começamos coletando evidência real.

No terminal, dentro da pasta do seu fork

  1. Escolha um domínio para investigar: uni9.br, github.com ou outro que você use.
  2. Rode nslookup SEU-DOMINIO e leia a saída: o servidor DNS consultado, o nome e o endereço devolvido.
  3. Copie a saída inteira. Ela vai virar um bloco de código no documento do passo 3.
  4. Rode ping SEU-DOMINIO e confira que o IP que aparece é o mesmo que o nslookup devolveu.

Se o nslookup não existir na sua máquina, use dig SEU-DOMINIO no Linux ou no macOS. Em rede corporativa o servidor consultado pode ser interno: registre o que aparecer, é evidência igual.

Laboratório, passo 2 de 4: a aba Network do DevTools [3]

Agora a evidência do HTTP. Abra no navegador o mesmo site que você investigou no passo anterior.

No navegador
