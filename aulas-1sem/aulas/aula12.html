Como o ClinicaContext chega ao Controller [1]

Você nunca escreve new ClinicaContext() dentro de uma action. Quem cria, entrega e descarta o contexto é o contêiner de serviços do ASP.NET Core.

Takeaway

Se o construtor pedir um tipo que ninguém registrou em Program.cs, o contêiner não sabe construir o Controller e a requisição falha com InvalidOperationException. Registro e construtor andam sempre juntos.

12 Injeção de dependência

Por que toda operação de banco é assíncrona [4]

Consultar o MySQL é esperar por outro processo. A pergunta não é quanto tempo demora, é o que a thread do servidor faz enquanto espera.

Takeaway

Toda ida ao banco usa o método terminado em Async, e sempre com await. Sem o await, o que volta é uma Task, não a lista, e a View recebe um objeto que não sabe desenhar.

Consultar: você escreve C#, o EF Core escreve SQL [2]

O DbSet aceita LINQ. O EF Core traduz a expressão para SQL e só vai ao banco quando você pede o resultado, no ToListAsync ou no FirstOrDefaultAsync.

// Lista inteira, em ordem alfabética
var pacientes = await _context.Pacientes.OrderBy(p => p.Nome).ToListAsync();

// Um registro pela chave primária: o mais direto, e olha o cache antes de ir ao banco
var paciente = await _context.Pacientes.FindAsync(id);

// Um registro por qualquer condição; devolve null se não achar nada
var porCpf = await _context.Pacientes.FirstOrDefaultAsync(p => p.Cpf == cpf);

// Filtro traduzido para a cláusula WHERE, executado no MySQL, não em memória
var busca = await _context.Pacientes.Where(p => p.Nome.Contains(termo)).ToListAsync();

O SQL gerado aparece no terminal em que a aplicação está rodando: SELECT p.Id, p.Cpf, p.Nome ... FROM Pacientes AS p ORDER BY p.Nome. Leia esse log: é ele que denuncia consulta pesada.

O identificador que não existe

A URL é editável pelo usuário. Alguém vai digitar /Pacientes/Details/9999, e esse paciente não existe. O EF Core devolve null, sem erro, e a decisão é sua.

Sem tratamento

  • A View recebe null e quebra ao ler Model.Nome.
  • O usuário vê uma página de erro, com pilha de exceção.

Com NotFound()

  • A resposta é um 404, que é a verdade sobre o recurso.
  • Duas linhas resolvem, em toda action que recebe um id.
public async Task<IActionResult> Details(int? id)
{
    if (id == null) return NotFound();                       // rota sem id
    var paciente = await _context.Pacientes.FirstOrDefaultAsync(p => p.Id == id);
    if (paciente == null) return NotFound();                 // id que não existe
    return View(paciente);
}

Gravar: Add, Update, Remove e o SaveChangesAsync [3]

Os três primeiros métodos não tocam no banco: eles anotam a intenção no rastreador de mudanças. Quem abre a transação e emite o SQL é o SaveChangesAsync, uma vez só.

_context.Add(paciente)
→
estado: Added
→
await SaveChangesAsync()
→
INSERT no MySQL
O que você escreveEstado registradoSQL emitido no SaveChangesAsync
_context.Add(paciente)AddedINSERT INTO Pacientes ..., e o Id volta preenchido
_context.Update(paciente)ModifiedUPDATE Pacientes SET ... WHERE Id = @id
_context.Pacientes.Remove(p)DeletedDELETE FROM Pacientes WHERE Id = @id
Takeaway

Esqueceu o await _context.SaveChangesAsync()? A aplicação não acusa erro nenhum, a tela redireciona normalmente e o registro simplesmente não existe no banco. É o defeito mais comum desta aula.

Post-Redirect-Get: por que redirecionar depois de gravar [1]

O navegador guarda a última requisição feita. Se ela for o POST, apertar F5 reenvia o formulário inteiro, e o EF Core grava de novo, sem reclamar de nada.

Takeaway

Toda action de POST que grava termina em RedirectToAction, nunca em View. A única exceção é a validação que falhou: aí nada foi gravado, e devolver a View é o certo.

A mensagem que sobrevive ao redirecionamento: TempData

O redirecionamento resolve a duplicidade e cria um problema novo: a action que gravou não é a que desenha a tela. ViewBag morre no caminho; TempData atravessa uma requisição.

// No PacientesController, logo depois de gravar
await _context.SaveChangesAsync();
TempData["Sucesso"] = $"Paciente {paciente.Nome} cadastrado com sucesso.";
return RedirectToAction(nameof(Index));
@* Em Views/Pacientes/Index.cshtml, no topo da tabela *@
@if (TempData["Sucesso"] != null)
{
    <p class="alerta-sucesso">@TempData["Sucesso"]</p>
}
Takeaway

TempData é lido uma vez e some. Se a mensagem aparecer de novo depois de um F5, ela foi gravada de novo, e isso é sinal de que o Post-Redirect-Get não está no lugar.

Excluir em duas etapas: o GET pergunta, o POST apaga

Exclusão por link é armadilha: um clique errado apaga um cadastro. GET nunca destrói dado.

// Etapa 1, GET: mostra a ficha e pergunta se é isso mesmo
public async Task<IActionResult> Delete(int? id)
{
    if (id == null) return NotFound();
    var paciente = await _context.Pacientes.FirstOrDefaultAsync(p => p.Id == id);
    if (paciente == null) return NotFound();
    return View(paciente);
}

// Etapa 2, POST: o formulário da tela de confirmação chega aqui
[HttpPost, ActionName("Delete")]
[ValidateAntiForgeryToken]
public async Task<IActionResult> DeleteConfirmed(int id)
{
    var paciente = await _context.Pacientes.FindAsync(id);
    if (paciente != null) _context.Pacientes.Remove(paciente);
    await _context.SaveChangesAsync();
    TempData["Sucesso"] = "Paciente excluído.";
    return RedirectToAction(nameof(Index));
}

Quiz de fixação

Por que redirecionar após um POST bem-sucedido, em vez de devolver a View diretamente?
  • A Porque o redirecionamento consome menos memória no servidor do que renderizar a View mais uma vez.
  • BPorque o Entity Framework Core exige um redirecionamento logo depois da chamada de SaveChangesAsync.
  • CPorque uma action anotada com [HttpPost] não pode retornar uma View, apenas um redirecionamento.
  • D Para evitar o reenvio duplicado do formulário quando o usuário atualiza a página, no padrão Post-Redirect-Get.

Laboratório, passo 4 de 6: o cadastro

Create em GET e em POST, o fim do Ciclo 3

  1. Create() em GET devolve a View vazia; o POST grava.
  2. Se ModelState.IsValid for falso, devolva a View com o objeto.
  3. Sendo válido: Add, SaveChangesAsync, TempData e RedirectToAction.
  4. Cadastre um paciente e confira a linha nova no MySQL Workbench.
[HttpPost, ValidateAntiForgeryToken]
public async Task<IActionResult> Create(Paciente paciente)
{
    if (!ModelState.IsValid) return View(paciente);
    _context.Add(paciente);
    await _context.SaveChangesAsync();
    TempData["Sucesso"] = $"Paciente {paciente.Nome} cadastrado com sucesso.";
    return RedirectToAction(nameof(Index));
}

Laboratório, passo 5 de 6: a edição

Ciclo 4, sozinho. A partir daqui o professor circula pela sala, e o roteiro completo está em labs/aula12-lab/.

Edit em GET e em POST

  1. No GET, carregue o paciente com FindAsync e devolva a View já preenchida.
  2. No POST, receba (int id, Paciente paciente) e recuse com NotFound() se id != paciente.Id.
  3. Guarde o Id em um campo oculto na View: sem ele, o POST chega com Id zero e o EF Core tenta um INSERT.
  4. Grave com Update e SaveChangesAsync, e redirecione com a mensagem em TempData.
if (id != paciente.Id) return NotFound();
if (!ModelState.IsValid) return View(paciente);
_context.Update(paciente);
await _context.SaveChangesAsync();
