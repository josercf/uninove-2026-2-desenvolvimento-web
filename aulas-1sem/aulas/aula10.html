O Model: o dado e a regra, no mesmo lugar

O Model do MVC não é só um saco de propriedades: ele descreve o que o dado é e o que torna esse dado válido. A classe Consulta nasce hoje, ainda sem anotações.

namespace ClinicaVida.Web.Models;

public class Consulta
{
    public int Id { get; set; }
    public int PacienteId { get; set; }        // qual paciente, pelo identificador
    public int MedicoId { get; set; }          // qual médico do corpo clínico
    public DateTime Data { get; set; }
    public TimeSpan Horario { get; set; }
    public string? Observacoes { get; set; }
}

E a especialidade? Ela não vira propriedade da Consulta: o médico já carrega a dele, em Medico.EspecialidadeId. Na tela a especialidade continua aparecendo, mas só para filtrar a lista de médicos. Guardar o mesmo dado em dois lugares é onde a divergência começa.

Model binding: do campo do formulário ao objeto C# [1]

O navegador envia pares de nome e valor. O ASP.NET Core casa cada nome com uma propriedade do parâmetro da action, converte o texto para o tipo certo e entrega o objeto pronto.

Quando o nome não casa, ninguém avisa. A propriedade simplesmente fica com o valor padrão do tipo: 0 para int, nulo para string. É o primeiro lugar onde olhar quando um campo chega vazio no servidor mesmo tendo sido preenchido na tela.

10 Model binding
7

Um formulário, duas actions com o mesmo nome

O par [HttpGet] e [HttpPost] é a espinha de todo formulário no MVC: uma action mostra, a outra recebe. Quando a validação falha, a segunda devolve a mesma View, agora com os erros.

Takeaway

Sucesso não devolve View, devolve redirecionamento. Sem isso, o paciente que atualizar a página de resposta reenvia o mesmo agendamento, e a clínica ganha uma consulta em duplicidade, exatamente o problema que este case veio resolver.

Tag Helpers: HTML que sabe do Model [3]

Um Tag Helper é um atributo que o servidor lê e substitui por HTML de verdade antes de a resposta sair. Quem escreve é você; quem preenche é o Razor.

@model ClinicaVida.Web.Models.Consulta

<form asp-controller="Consultas" asp-action="Agendar" method="post">
  <label asp-for="Data"></label>
  <input asp-for="Data" />
</form>

O que chega ao navegador, já com a rota resolvida e o valor do Model:

<form action="/Consultas/Agendar" method="post">
  <label for="Data">Data da consulta</label>
  <input type="date" id="Data" name="Data" value="2026-10-21"
         data-val="true" data-val-required="Informe a data da consulta." />

Por que não escrever o action à mão: asp-controller e asp-action pedem a URL ao roteamento. Se a rota mudar amanhã, o formulário continua apontando para o lugar certo.

10 Tag Helpers de formulário

Onde os erros aparecem, e o token antifalsificação [4]

Por campo: asp-validation-for

Escreve a mensagem daquele campo, e só dela, ao lado do próprio campo. É o lugar onde o paciente olha.

Resumo: asp-validation-summary

ModelOnly lista os erros que não pertencem a nenhum campo; All lista todos, no topo do formulário.

<div asp-validation-summary="ModelOnly" class="erro-resumo"></div>

<label asp-for="MedicoId"></label>
<select asp-for="MedicoId" asp-items="ViewBag.Medicos">
  <option value="">Selecione o médico</option>
</select>
<span asp-validation-for="MedicoId" class="erro-campo"></span>

O token antifalsificação: o Tag Helper de form injeta sozinho um campo oculto com um token, e [ValidateAntiForgeryToken] na action de POST exige esse token. É o que impede que um site qualquer, aberto em outra aba, poste um agendamento em nome do paciente logado.

Data Annotations: a regra escrita ao lado do dado [2]

Cada anotação é um atributo em cima da propriedade. Todas aceitam ErrorMessage, e nesta disciplina toda mensagem é escrita em português: quem lê é o paciente, não o programador.

AnotaçãoO que declara na Clínica Vida+
[Required]O campo não pode chegar vazio: a data da consulta, por exemplo
[StringLength]Tamanho máximo, e mínimo se quiser: 300 caracteres nas observações
[EmailAddress]O texto precisa ter forma de e-mail, para o aviso de confirmação
[Phone]O telefone de contato do paciente
[Range]Faixa de valores: usada para exigir que uma lista suspensa seja escolhida
[DataType]O papel do dado: Date, Time, Password. Define o type do input
[Display]O rótulo que aparece na tela, com acento e espaço, no lugar do nome da propriedade
[RegularExpression]Um formato exato, como a máscara do CPF

A mesma Consulta, agora anotada

using System.ComponentModel.DataAnnotations;

public class Consulta
{
    public int Id { get; set; }

    [Display(Name = "Paciente")]
    [Range(1, int.MaxValue, ErrorMessage = "Selecione o paciente.")]
    public int PacienteId { get; set; }        // MedicoId segue igual

    [Display(Name = "Data da consulta")]
    [Required(ErrorMessage = "Informe a data da consulta.")]
    [DataType(DataType.Date)]
    public DateTime Data { get; set; }         // Horario usa DataType.Time

    [Display(Name = "Observações")]
    [StringLength(300, ErrorMessage = "No máximo {1} caracteres.")]
    public string? Observacoes { get; set; }
}

As duas propriedades omitidas repetem o padrão da vizinha: MedicoId como PacienteId, e Horario como Data. O roteiro do laboratório traz a classe inteira.

ModelState: o relatório da validação [2]

Antes de a sua primeira linha executar, o framework já fez o binding e conferiu todas as anotações. O resultado chega em ModelState, e a decisão do que fazer com ele é sua.

[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Agendar(Consulta consulta)
{
    if (!ModelState.IsValid)
    {
        CarregarListas();          // as listas suspensas não sobrevivem ao POST
        return View(consulta);     // mesma View, com os valores e os erros
    }

    consulta.Id = ClinicaEmMemoria.Consultas.Count + 1;
    ClinicaEmMemoria.Consultas.Add(consulta);
    return RedirectToAction(nameof(Confirmacao), new { id = consulta.Id });
}

A armadilha do dia: esquecer o CarregarListas() no caminho do erro. O formulário volta com as mensagens certas e os select vazios, porque o ViewBag só existe durante uma requisição.

10 ModelState no Controller
14

A regra de ouro da aula [2]

As mesmas anotações geram os atributos data-val que a biblioteca de validação do navegador lê. Bonito e instantâneo, e completamente contornável.

Regra de ouro

Validação no cliente é conforto; validação no servidor é segurança. A do cliente evita uma viagem à toa. A do servidor é a única que ninguém consegue desligar, e por isso ela nunca é opcional.

Demonstração de 30 segundos: abra o DevTools, apague o atributo required do campo obrigatório e envie. O navegador deixa passar; o servidor recusa com a mesma mensagem que você escreveu na anotação.

Quiz de fixação

Um formulário é enviado com um campo obrigatório em branco, e a validação do cliente foi contornada. O que acontece na action de POST?
  • AA action executa, ModelState.IsValid fica falso e cabe ao Controller devolver a View com as mensagens de erro.
  • B A action não chega a ser executada, porque o framework bloqueia a requisição antes do model binding.
  • CO Entity Framework Core rejeita o registro no SaveChangesAsync e devolve à action uma exceção de validação.
  • D O navegador exibe uma tela de erro do servidor, porque a propriedade obrigatória ficou sem valor no Model.

// using ClinicaVida.Web.Models, Microsoft.AspNetCore.Mvc e Mvc.Rendering

public class ConsultasController : Controller
{
    [HttpGet]
    public IActionResult Agendar()
    {
        CarregarListas();
        return View(new Consulta { Data = DateTime.Today });
    }

    private void CarregarListas()
    {
        ViewBag.Pacientes = new SelectList(ClinicaEmMemoria.Pacientes, "Id", "Nome");
        ViewBag.Medicos   = new SelectList(ClinicaEmMemoria.Medicos,   "Id", "Nome");
    }
}

Laboratório, passo 5 de 6: o POST e o ModelState

A segunda action Agendar, mesmo nome e verbo diferente. Teste primeiro o caminho do erro: envie o formulário vazio. A data futura é regra de negócio, não formato: nenhuma anotação sabe o que é hoje, e por isso ela entra no relatório pela mão do Controller, com ModelState.AddModelError.

[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Agendar(Consulta consulta)
{
    if (consulta.Data.Date < DateTime.Today)
        ModelState.AddModelError("Data", "A consulta precisa ser em uma data futura.");

    if (!ModelState.IsValid)
    {
        CarregarListas();
        return View(consulta);
    }

    consulta.Id = ClinicaEmMemoria.Consultas.Count + 1;
    ClinicaEmMemoria.Consultas.Add(consulta);
    return RedirectToAction(nameof(Confirmacao), new { id = consulta.Id });
}

Laboratório, passo 6 de 6: a tela de confirmação

O agendamento válido não devolve uma View: ele redireciona. Assim, atualizar a página de confirmação não reenvia a consulta.

[HttpGet]
public IActionResult Confirmacao(int id)
{
    var consulta = ClinicaEmMemoria.Consultas.FirstOrDefault(c => c.Id == id);
    if (consulta is null) return NotFound();

    ViewBag.NomePaciente = ClinicaEmMemoria.Pacientes.First(p => p.Id == consulta.PacienteId).Nome;
    ViewBag.NomeMedico   = ClinicaEmMemoria.Medicos.First(m => m.Id == consulta.MedicoId).Nome;
    return View(consulta);
}
Confira

A View Confirmacao.cshtml mostra paciente, médico, data e horário. A barra de endereços precisa terminar em /Consultas/Confirmacao/1, e não em /Consultas/Agendar.

A limitação que sobra, e a prévia da Aula 11

Faça o teste antes de fechar o notebook: agende uma consulta, veja a confirmação, pare a aplicação com Ctrl+C e rode dotnet run de novo. A consulta sumiu.

formulário
→
model binding
→
validação no servidor

O elo que falta é o último: a lista em memória vive enquanto o processo vive. Uma clínica de verdade precisa que o agendamento continue lá amanhã, depois de reiniciar o servidor, e visível para a recepção em outra máquina.
