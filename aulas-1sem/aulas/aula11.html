O que um ORM resolve [1]

Seu código pensa em objetos; o MySQL guarda tabelas. O ORM faz a tradução nas duas direções.

Sem ORM, na mão

var sql = "SELECT Id, Nome FROM Pacientes"
        + " WHERE Id = @id";
using var cmd = new MySqlCommand(sql, conn);
cmd.Parameters.AddWithValue("@id", id);
using var leitor = cmd.ExecuteReader();
leitor.Read();
var p = new Paciente {
    Id   = leitor.GetInt32(0),
    Nome = leitor.GetString(1)
};

Com o EF Core

var p = await _context.Pacientes.FindAsync(id);
  • O SQL é gerado pelo EF Core, já parametrizado.
  • O compilador confere nome e tipo de cada campo.
  • Trocar de banco não reescreve a aplicação.
Takeaway

O ORM não substitui o banco nem o SQL: ele escreve o SQL por você, a partir das suas classes.

O MySQL na sua máquina [4]

Antes de qualquer linha de C#: o servidor precisa estar no ar e aceitar o seu usuário. Três verificações, nesta ordem.

1. O servidor está instalado

MySQL Community Server 8.0 ou superior, mais o MySQL Workbench para inspecionar as tabelas depois.

2. O serviço está rodando

Serviço MySQL80 no Windows, brew services list no macOS. Porta padrão: 3306.

3. O usuário existe

Um usuário de aplicação, com permissão apenas no banco da clínica. Nunca a aplicação como root.

CREATE USER 'clinicaapp'@'localhost' IDENTIFIED BY 'Senha123';
GRANT ALL PRIVILEGES ON clinicavida.* TO 'clinicaapp'@'localhost';
FLUSH PRIVILEGES;

Repare: o banco clinicavida ainda não existe, e o GRANT funciona mesmo assim. Quem vai criar o banco é a migration, no Ciclo 4.

Os pacotes e o registro do contexto [3]

O EF Core sozinho não fala MySQL: quem fala é o provedor. Nesta disciplina, o provedor é o Pomelo.EntityFrameworkCore.MySql.

dotnet tool install --global dotnet-ef        # a ferramenta de linha de comando
dotnet add package Pomelo.EntityFrameworkCore.MySql
dotnet add package Microsoft.EntityFrameworkCore.Design

Em Program.cs, antes de builder.Build(), o contexto entra no contêiner de injeção de dependência:

var conexao = builder.Configuration.GetConnectionString("DefaultConnection");

builder.Services.AddDbContext<ClinicaContext>(opcoes =>
    opcoes.UseMySql(conexao, ServerVersion.AutoDetect(conexao)));
Takeaway

Registrado assim, o ClinicaContext passa a ser injetado em qualquer Controller pelo construtor. É disso que a Aula 12 vive.

Anatomia da connection string [3]

Como a URL da Aula 02, ela não é um texto solto: é um endereço com cinco partes, cada uma lida por um pedaço diferente da conexão.

Senha de produção nunca vai para o repositório. Em sala, uma senha local no appsettings.Development.json resolve. Em produção, a senha vem de variável de ambiente ou de um cofre de segredos, e o arquivo com a senha entra no .gitignore. [5]

O DbContext e os DbSet da clínica [1]

O DbContext é a sessão com o banco: ele conhece o modelo, guarda o que mudou e traduz tudo para SQL. Cada DbSet<T> é uma tabela.

using Microsoft.EntityFrameworkCore;
using ClinicaVida.Web.Models;

namespace ClinicaVida.Web.Data;

public class ClinicaContext : DbContext
{
    public ClinicaContext(DbContextOptions<ClinicaContext> options) : base(options) { }

    public DbSet<Paciente> Pacientes => Set<Paciente>();
    public DbSet<Medico> Medicos => Set<Medico>();
    public DbSet<Especialidade> Especialidades => Set<Especialidade>();
    public DbSet<Consulta> Consultas => Set<Consulta>();
}
Takeaway

O nome da propriedade DbSet vira o nome da tabela: Pacientes, e não Paciente. Quatro DbSet, quatro tabelas.

Migration: o commit do seu banco de dados [2]

Uma migration é um arquivo C# versionado no Git, com dois métodos: Up aplica a mudança, Down desfaz. Ele descreve o esquema, não os dados do dia a dia.

// Migrations/20261014193000_InicialClinicaVida.cs
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.CreateTable(
        name: "Pacientes",
        columns: table => new
        {
            Id = table.Column<int>(nullable: false)
                .Annotation("MySql:ValueGenerationStrategy", IdentityColumn),
            Nome = table.Column<string>(maxLength: 120, nullable: false)
        },
        constraints: table => table.PrimaryKey("PK_Pacientes", x => x.Id));
}

protected override void Down(MigrationBuilder mb)
    => mb.DropTable(name: "Pacientes");
Takeaway

Migration commitada é banco reproduzível: um colega clona, roda um comando e tem o mesmo esquema.

O fluxo da migration, da classe à tabela [2]

Dois comandos, cinco etapas. Confundir os dois comandos é o erro mais comum do laboratório de hoje: um escreve o arquivo, o outro mexe no banco.

Takeaway

migrations add escreve o arquivo; database update mexe no banco. Nunca o contrário.

Errou a migration? Reverter e remover [2]

Ninguém acerta o esquema de primeira. Saber qual comando usar é o que separa o conserto tranquilo do banco quebrado.

ComandoQuando usar
dotnet ef migrations listVer quais migrations existem e quais já foram aplicadas
dotnet ef migrations removeApagar a última migration ainda não aplicada ao banco
dotnet ef database update NomeVoltar o banco ao estado daquela migration; com 0, desfaz todas
dotnet ef migrations scriptGerar o SQL, sem executar, para revisão antes de produção
Takeaway

Nunca edite à mão uma migration já aplicada, nem apague o arquivo pelo explorador: reverta com database update e só então use migrations remove.

Carga inicial de dados com HasData [2]

Um banco vazio não demonstra nada. As especialidades da Clínica Vida+ não mudam todo dia: elas fazem parte do esquema e entram pela própria migration.

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Especialidade>().HasData(
        new Especialidade { Id = 1, Nome = "Clínica Geral", Descricao = "Rotina e encaminhamentos" },
        new Especialidade { Id = 2, Nome = "Cardiologia",   Descricao = "Coração e circulação" },
        new Especialidade { Id = 3, Nome = "Pediatria",     Descricao = "Crianças e adolescentes" },
        new Especialidade { Id = 4, Nome = "Dermatologia",  Descricao = "Pele, cabelos e unhas" }
    );
}
Takeaway

Em HasData a chave primária é obrigatória e escrita à mão: o EF Core precisa do Id para saber se aquela linha já existe. Alterou a lista? Uma nova migration cuida da diferença.

Quiz de fixação

O que o comando dotnet ef database update faz?
  • AGera as classes de entidade a partir de um banco já existente, invertendo o sentido do mapeamento.
  • BApaga o banco de dados e o recria vazio, descartando as tabelas e os dados que existiam antes.
  • CAplica ao banco as migrations pendentes, criando ou alterando as tabelas conforme o modelo atual.
  • DAtualiza os pacotes NuGet do projeto para a versão mais recente, inclusive os do próprio EF Core.

O que fica desta aula, e o que vem na Aula 12

ORM e EF Core

Classe de um lado, tabela do outro. O EF Core escreve o SQL a partir do seu modelo, e o provedor Pomelo fala MySQL.

DbContext e DbSet

O ClinicaContext é a sessão com o banco. Quatro DbSet, quatro tabelas, registradas na injeção de dependência.

Migrations

O esquema virou código versionado. add escreve o arquivo, update mexe no banco, __EFMigrationsHistory guarda o que já foi.
