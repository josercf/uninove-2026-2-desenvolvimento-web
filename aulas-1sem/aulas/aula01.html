Por que versionar: o problema real

Você já viveu isso: trabalho_final.docx, trabalho_final_v2.docx, trabalho_final_agora_vai.docx. Sem histórico, sem volta atrás e sem resposta para "quem mudou isso e por quê". O problema fica sério no instante em que a segunda pessoa toca no mesmo arquivo.

Takeaway

Versionar não é fazer backup. É guardar a história das decisões, com autor, data e motivo, de um jeito que permite voltar a qualquer ponto dela.

01 Por que versionar
9

Da cópia de pasta ao Git [2]

A virada decisiva foi sair do modelo centralizado e síncrono, com um servidor único que precisa estar no ar, para o distribuído, em que cada clone é um repositório completo, com todo o histórico.

Antes de 1972 Cópia manual Duplicar a pasta e renomear. Perdeu o disco, perdeu tudo, e ninguém sabe qual cópia vale.
1990 CVS Primeiro servidor central. Vários desenvolvedores no mesmo projeto, mas com merge frágil.
2000 Subversion Centralizado e síncrono. Commitar exige rede, e o servidor é ponto único de falha.
2005 Git Nasce para o kernel do Linux. Distribuído e assíncrono: clone integral, commit e branch offline.
2008 até hoje GitHub e GitLab O Git vira plataforma: Pull Request, revisão de código e automação sobre o mesmo histórico.

Centralizado, até 2005

O histórico mora em um servidor único, que precisa estar no ar. Commitar exige rede, e a queda do servidor para o time inteiro.

Distribuído, com o Git

Cada clone é um repositório completo, com todo o histórico. Commit e branch funcionam sem internet, e compartilhar é um passo à parte, o push.

Takeaway

O Git venceu porque separou o ato de versionar do ato de compartilhar. Você comita sem internet e sincroniza quando quiser.

01 Evolução do controle de versão
10

O que é, de fato, um commit [2]

Um commit não é a lista de linhas alteradas. É uma fotografia completa e imutável do projeto inteiro, endereçada por um hash e ligada ao commit anterior. O diff que você vê na tela é calculado entre duas fotografias; não é o que fica guardado.

Cada commit aponta para o anterior

Essa corrente é a história do projeto. Percorrê-la de trás para frente é o que permite git log e git revert.

Imutável por construção

O hash vem do próprio conteúdo. Alterar um commit antigo muda o hash dele e o de todos os seguintes: a adulteração fica evidente.

O tamanho certo

Uma mudança coerente, que você reverteria sozinha. "Fim do dia" não é commit; "corrige o horário duplicado na agenda" é.

01 O commit
11

O que é, de fato, uma branch [2]

Uma branch não é uma cópia do projeto: é um ponteiro leve para um commit, por isso criar uma é instantâneo. Pense em linhas do tempo paralelas: do mesmo ponto da história você abre quantas realidades quiser, testa cada uma sem risco, descarta as que falharam e traz de volta só a que funcionou.

Na prática

Como a branch é só um ponteiro, trocar de branch é o Git reescrever seus arquivos para o estado daquele commit. Por isso ele reclama quando há trabalho não commitado: não há onde guardar o que você ainda não salvou.

O ecossistema GitHub [3]

O Git é a ferramenta que roda na sua máquina. O GitHub é a plataforma que hospeda o repositório e acrescenta colaboração em volta dele.

Repositório remoto

A cópia do projeto hospedada na nuvem. push envia seus commits para lá, pull traz os dos outros.

Fork e clone

O fork cria uma cópia do repositório sob a sua conta. O clone traz essa cópia para a sua máquina.

Issues e Pull Request

A issue registra o que precisa ser feito. O Pull Request é onde o código é discutido e revisado antes de entrar na main.

Actions e Pages

O Actions automatiza tarefas a cada push. O Pages publica um site direto do repositório, sem servidor próprio.

O README.md é o cartão de visitas do repositório, e o seu histórico público de commits é portfólio profissional. Recrutador lê perfil do GitHub. Escolha um nome de usuário que você mostraria numa entrevista.

Quiz de fixação

O que um commit representa no Git?
  • A Apenas as linhas alteradas no arquivo desde o commit anterior do projeto.
  • B Um backup do arquivo que está aberto no editor no momento da gravação.
  • C Uma fotografia completa e imutável do projeto, ligada ao commit anterior.
  • D Uma cópia do repositório remoto guardada na sua própria máquina local.

Laboratório, passo 2 de 5: clonar o fork [4]

O clone traz o repositório inteiro, com todo o histórico, para a sua máquina. Troque SEU-USUARIO pelo seu nome de usuário do GitHub.

git --version

git clone https://github.com/SEU-USUARIO/uninove-2026-2-clinica-vida.git
cd uninove-2026-2-clinica-vida

git log --oneline

Repare no git log: o histórico do projeto veio junto. Isso é o Git ser distribuído. Abra a pasta no editor e leia o README.md antes de seguir.

01 Laboratório, passo 2, clone
16

Laboratório, passo 3 de 5: identidade no Git

A identidade é o que assina cada commit. Sem ela configurada, o seu trabalho não é atribuído a você.

git config --global user.name "Nome Sobrenome"
git config --global user.email "email@exemplo.com"

git config user.name
git config user.email

O e-mail precisa ser o mesmo cadastrado no GitHub. Se for outro, os commits aparecem no repositório mas não contam no seu perfil, e o checkpoint da aula fica sem dono.

Checkpoint

O professor passa de mesa em mesa conferindo que o clone funcionou e que os dois últimos comandos devolvem o seu nome e o seu e-mail.

Laboratório, passo 4 de 5: editar o README

Acrescente ao README.md do seu fork uma seção de identificação, com nome completo, RA e turma.

## Identificação

- Nome completo: Ana Souza

git status              # o README aparece como modificado
git add README.md
git status              # agora ele aparece pronto para o commit

O git add não salva nada: ele escolhe o que vai entrar na próxima fotografia. É por isso que o git status muda de resposta entre um comando e outro.

Laboratório, passo 5 de 5: commit e push

Agora a fotografia é tirada e enviada para o GitHub.

git commit -m "docs: identificação do aluno no README"

git log --oneline       # o seu commit, com o hash, no histórico

git push

Repare no padrão da mensagem: verbo no presente, escopo curto e a intenção explícita. Uma mensagem boa responde "por que" para quem ler o histórico daqui a seis meses.

Confira

Atualize a página do seu fork no GitHub. O commit precisa aparecer no histórico, com o seu nome ao lado.
