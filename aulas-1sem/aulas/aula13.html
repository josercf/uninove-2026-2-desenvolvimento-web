A solução: um crachá que o navegador devolve toda vez [4]

Um cookie é um par nome e valor que o servidor manda no cabeçalho Set-Cookie. O navegador guarda e o devolve, sozinho, no cabeçalho Cookie, em toda requisição seguinte ao mesmo domínio.

13 O fluxo do cookie
7

Os atributos do cookie são a segurança dele [3]

O par nome e valor é a parte fácil. O que separa um cookie seguro de um vazamento são os atributos depois do ponto e vírgula.

AtributoO que fazNa Clínica Vida+
HttpOnlyEsconde o cookie do JavaScript da páginaSempre. Script injetado não lê o crachá
SecureSó trafega sobre HTTPSSempre. Sem ele, o crachá vai em texto claro
SameSiteControla o envio em requisição vinda de outro siteLax, o padrão do ASP.NET Core
ExpiresValidade; sem ela morre ao fechar o navegador30 dias na unidade preferida
Domain, PathDelimitam a quais endereços o cookie é enviadoPath=/, vale para a aplicação inteira

Limite de tamanho: cerca de 4 KB por cookie, e tudo sobe em toda requisição, inclusive nas de imagem e CSS.

Gravar e ler um cookie no ASP.NET Core

Dentro de qualquer Controller, Response e Request já estão disponíveis. Gravar é acrescentar um cabeçalho na resposta; ler é consultar o cabeçalho que veio na requisição.

Gravar, na resposta

Response.Cookies.Append("unidade-preferida", "Tatuapé",
    new CookieOptions
    {
        Expires  = DateTimeOffset.UtcNow.AddDays(30),
        HttpOnly = true,
        Secure   = true,
        SameSite = SameSiteMode.Lax,
        IsEssential = true
    });

Ler, na requisição

if (Request.Cookies.TryGetValue(
        "unidade-preferida", out var unidade))
{
    ViewBag.Unidade = unidade;
}

// Apagar é sobrescrever com data no passado:
Response.Cookies.Delete("unidade-preferida");
Takeaway

O valor que volta é sempre string, e sempre veio do computador do usuário. Trate cookie como campo de formulário: valide antes de confiar.

13 Cookies no ASP.NET Core
9

Dado de paciente é dado sensível

Cookie fica gravado no disco de uma máquina que não é sua, muitas vezes compartilhada, e viaja em toda requisição. Na Clínica Vida+ isso tem peso legal, não só técnico.

Nunca em um cookie

  • CPF, nome completo e data de nascimento.
  • Especialidade, diagnóstico ou motivo da consulta.
  • Qualquer coisa que revele que a pessoa é paciente.
  • Um Id de paciente sem nada que o proteja.

Pode ir, com atributos corretos

  • Um identificador de sessão opaco e sorteado.
  • A unidade da clínica preferida pelo usuário.
  • Preferências de exibição, como fonte maior.
  • O aceite do aviso de cookies.

LGPD, Lei nº 13.709 de 2018: dado sobre saúde é dado pessoal sensível e tem regra mais dura de tratamento e de consentimento. Uma escolha de especialidade guardada no navegador do balcão da recepção é histórico clínico exposto a quem chegar depois.

Sessão: o dado fica no servidor, só o crachá viaja [2]

A sessão resolve o limite de 4 KB e o risco de privacidade: o navegador carrega apenas um identificador sorteado, e o conteúdo fica guardado do lado do servidor.

// Program.cs, antes do builder.Build()
builder.Services.AddDistributedMemoryCache();
builder.Services.AddSession(options =>
{
    options.IdleTimeout = TimeSpan.FromMinutes(20);
    options.Cookie.Name = ".ClinicaVida.Sessao";
    options.Cookie.HttpOnly = true;
    options.Cookie.IsEssential = true;
});
app.UseRouting()
→
app.UseSession()
→
app.UseAuthorization()
→
app.MapControllerRoute()
Takeaway

A ordem no pipeline não é decoração. UseSession depois de UseRouting e antes do mapeamento das rotas; fora daí, HttpContext.Session lança exceção no primeiro acesso.

Ler e gravar em HttpContext.Session [2]

A sessão guarda bytes, e a API expõe dois pares prontos: texto e inteiro. Para qualquer outra coisa, serialize o objeto em JSON e guarde o texto.

Texto e inteiro, direto

HttpContext.Session.SetInt32("MedicoId", 7);
HttpContext.Session.SetString("Unidade", "Tatuapé");

int? medicoId =
    HttpContext.Session.GetInt32("MedicoId");
string? unidade =
    HttpContext.Session.GetString("Unidade");

HttpContext.Session.Remove("MedicoId");
HttpContext.Session.Clear();

Objeto, serializado em JSON

var rascunho = new Consulta { MedicoId = 7 };

HttpContext.Session.SetString("Rascunho",
    JsonSerializer.Serialize(rascunho));

var json = HttpContext.Session.GetString("Rascunho");
var volta = json is null
    ? null
    : JsonSerializer.Deserialize<Consulta>(json);
Takeaway

GetInt32 devolve int? e GetString devolve string?: null significa que a chave nunca existiu ou que os 20 minutos de inatividade expiraram. Sempre trate esse null.

Onde vive cada um: cookie, sessão e TempData

Os três guardam estado, e os três dependem do mesmo crachá no cabeçalho. O que muda é onde o dado fica e quanto tempo ele dura.

13 Cookie, sessão e TempData

Demonstração: um agendamento em duas etapas

A etapa 1 guarda a escolha e redireciona. A etapa 2 recupera o que foi guardado e, se não achar nada, manda o usuário de volta em vez de quebrar.

Etapa 1: gravar e redirecionar

[HttpPost]
public IActionResult Agendar(int medicoId)
{
    HttpContext.Session.SetInt32(
        "AgendamentoMedicoId", medicoId);

    return RedirectToAction(nameof(AgendarHorario));
}

Etapa 2: recuperar e se defender

[HttpGet]
public IActionResult AgendarHorario()
{
    var medicoId = HttpContext.Session
        .GetInt32("AgendamentoMedicoId");

    if (medicoId is null)
    {
        TempData["Aviso"] = "Escolha o médico antes.";
        return RedirectToAction(nameof(Agendar));
    }
    return View();
}
Takeaway

Toda etapa que depende da anterior começa conferindo a sessão. O usuário digita a URL na barra de endereços, e o servidor não pode contar com um caminho feliz.

Quiz de fixação

Por padrão, onde ficam guardados os dados de uma sessão do ASP.NET Core?
  • A No servidor, com o navegador guardando apenas o identificador da sessão em um cookie enviado a cada requisição.
  • B No navegador do usuário, inteiros dentro do próprio cookie, que trafega completo a cada requisição feita.
  • C No banco de dados da aplicação, gravados pelo EF Core a cada alteração que for feita no conteúdo da sessão.
  • D Na query string de cada URL da aplicação, acrescentada pelo framework no momento em que a página é renderizada.

O que fica desta noite e a prévia da Aula 14

O protocolo esquece

O HTTP trata cada requisição como a primeira. Estado é algo que a aplicação constrói por cima, não algo que o protocolo entrega.

O cookie é o crachá

Um par nome e valor no cabeçalho, com HttpOnly, Secure e SameSite. Pequeno, visível ao usuário e nunca confiável sem validação.

A sessão é o armário

O dado fica no servidor e só o identificador viaja. É o que sustenta o fluxo de duas etapas e, na Aula 15, o usuário logado.

Prévia da Aula 14: hoje, escolher a especialidade recarrega a página inteira só para trocar a lista de médicos. São dezenas de kilobytes de HTML redesenhados para atualizar um único select. Na próxima aula a página aprende a pedir só o pedaço que mudou, com fetch, JSON e uma action que devolve dados em vez de tela.

Antes de sair

Commit e push na branch feature/sessao-agendamento. O trabalho de hoje é o ponto de partida do laboratório da Aula 14.
