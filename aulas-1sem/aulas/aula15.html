De onde viemos: o agendamento fluido da Aula 14

Você entregou a consulta de médicos e de horários livres por AJAX, sem recarregar a página: MedicosPorEspecialidade e HorariosDisponiveis devolvendo JSON, o fetch montando a lista no DOM, com indicação de carregamento e tratamento de erro.

O que a Clínica Vida+ já faz

  • Guarda pacientes, médicos e consultas no MySQL.
  • Agenda em duas etapas, com sessão e cookie.
  • Devolve JSON para a tela sem recarregar nada.
  • Cadastra, edita e exclui paciente pela recepção.

O buraco que ninguém tapou

  • Qualquer pessoa com o endereço abre a agenda.
  • /Pacientes lista CPF e telefone para o mundo.
  • Um clique em Excluir apaga um paciente real.
  • O sistema não sabe dizer quem fez cada coisa.

Dado de saúde é dado sensível. Hoje a Clínica Vida+ publica o prontuário administrativo da clínica para quem souber digitar a URL. Esta aula fecha essa porta, e ela tem duas fechaduras: autenticação e autorização.

Duas perguntas diferentes, na ordem certa [1]

São palavras parecidas e conceitos distintos. Autenticar é provar quem se é. Autorizar é decidir o que essa pessoa pode fazer. Uma vem sempre antes da outra.

Takeaway

As duas decisões acontecem no servidor, a cada requisição. Nenhuma delas depende do que a tela mostra ou deixa de mostrar ao usuário.

Duas contas, a mesma senha, hashes diferentes [4]

Ana e Bruno escolheram, por coincidência, a mesma senha. Olhe o que o banco guarda em cada caso.

Takeaway

Você não escreve nada disso: CreateAsync gera o salt, aplica a derivação e grava o resultado em PasswordHash. O que se espera de você é não inventar o seu próprio esquema no lugar deste.

15 Hash e salt
6

Hash não é criptografia [3]

A confusão é comum e tem consequência prática: quem acha que a senha está "criptografada" acredita que existe um jeito de lê-la de volta. Não existe, e é isso que se quer.

Takeaway

Guardar senha "criptografada" é defeito, não elogio: significa que existe uma chave capaz de devolver a senha de todo mundo. Senha se guarda como hash, e hash não tem volta.

15 Hash não é criptografia
7

O login acontece uma vez; o cookie sustenta o resto [1]

O HTTP continua sem estado, exatamente como na Aula 13. A autenticação por cookie resolve isso do mesmo jeito: um cookie, emitido pelo servidor, viaja em toda requisição seguinte.

Takeaway

É o mesmo cookie da Aula 13, com uma diferença: este é assinado e cifrado pelo servidor. Adulterar o valor no navegador não vira "sou a Ana", vira cookie inválido e volta para o login.

8

O que o ASP.NET Core Identity traz pronto [1]

Ninguém escreve o próprio esquema de senhas em produção. O Identity é a implementação que já vem no framework, com o hash, o salt, o cookie e o modelo de usuários e perfis.

Os serviços que você vai injetar

  • UserManager<IdentityUser>: cria usuário, aplica o hash, associa perfis.
  • SignInManager<IdentityUser>: valida a senha, emite e derruba o cookie.
  • RoleManager<IdentityRole>: cria e consulta os perfis.
  • O hasher de senha e a proteção do cookie, configurados por padrão.

As sete tabelas da migration

  • AspNetUsers, com PasswordHash e SecurityStamp.
  • AspNetRoles e AspNetUserRoles, os perfis e o vínculo.
  • AspNetUserClaims e AspNetRoleClaims.
  • AspNetUserLogins e AspNetUserTokens.
Takeaway

Não existe coluna de senha em lugar nenhum. O que o banco guarda é PasswordHash, e o valor dele não volta a ser senha por caminho nenhum.

Instalar e ligar o Identity no Program.cs [1]

dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore
builder.Services.AddIdentity<IdentityUser, IdentityRole>(opcoes =>
{
    opcoes.Password.RequiredLength = 8;
    opcoes.Password.RequireNonAlphanumeric = false;
    opcoes.User.RequireUniqueEmail = true;
})
.AddEntityFrameworkStores<ClinicaContext>();

builder.Services.ConfigureApplicationCookie(opcoes =>
{
    opcoes.LoginPath = "/Conta/Login";
    opcoes.AccessDeniedPath = "/Conta/AcessoNegado";
});

A ordem no pipeline não é negociável: app.UseAuthentication() vem antes de app.UseAuthorization(), e os dois depois de app.UseRouting(). Invertidos, o HttpContext.User ainda está vazio quando a autorização decide, e todo mundo é barrado.

Um contexto só: o ClinicaContext muda de pai [1]

O Identity precisa de um DbContext. Em vez de criar um segundo, o contexto da Aula 11 passa a herdar de IdentityDbContext<IdentityUser>: uma cadeia de migrations, um banco coerente.

public class ClinicaContext : IdentityDbContext<IdentityUser>
{
    public ClinicaContext(DbContextOptions<ClinicaContext> opcoes)
        : base(opcoes) { }

    public DbSet<Paciente> Pacientes => Set<Paciente>();
    // os demais DbSet continuam como estavam

    protected override void OnModelCreating(ModelBuilder builder)
    {
        base.OnModelCreating(builder);   // esta linha é obrigatória
        builder.Entity<Especialidade>().HasData(/* ... */);
    }
}

Esqueceu o base.OnModelCreating(builder)? A aplicação nem sobe: IdentityUserLogin<string> requires a primary key. É a classe base que mapeia as tabelas do Identity.

A migration que a troca de herança gera

Trocar a classe base muda o modelo, e todo modelo alterado vira migration. As suas quatro tabelas continuam onde estavam; a migration só acrescenta as sete do Identity.

dotnet ef migrations add IdentityClinicaVida
dotnet ef database update

Antes, no banco clinicavida

  • Especialidades, Medicos, Pacientes e Consultas.
  • Uma migration aplicada, a InicialClinicaVida.
  • Nenhuma noção de usuário.

Depois, no mesmo banco

  • As mesmas quatro tabelas, intactas e com os dados.
  • Mais as sete AspNet..., criadas pela nova migration.
  • Duas migrations na mesma cadeia, na mesma pasta.
Takeaway

Confira a migration gerada antes de aplicá-la. Se ela mandar apagar alguma das suas tabelas, o modelo saiu do lugar e o database update levaria os dados junto.

O ContaController, escrito à mão, em MVC

Continuamos em MVC: Controller, action e View. Quem conversa com o Identity é o SignInManager, injetado pelo construtor como qualquer outro serviço.

[HttpPost]
[ValidateAntiForgeryToken]
public async Task<IActionResult> Login(LoginViewModel modelo)
{
    if (!ModelState.IsValid) return View(modelo);

    var resultado = await _signInManager.PasswordSignInAsync(
        modelo.Email, modelo.Senha, modelo.Lembrar,
        lockoutOnFailure: true);

    if (resultado.Succeeded) return RedirectToAction("Index", "Home");
    ModelState.AddModelError("", "E-mail ou senha inválidos.");
    return View(modelo);
}

A mensagem de erro é genérica de propósito: "esse e-mail não existe" conta a um atacante quais contas a clínica tem. Logout chama SignOutAsync, e Registrar chama CreateAsync, que já aplica o hash com salt.

Três atributos, e a regra fica no código [2]

AtributoO que acontece com a requisição
[Authorize]Só entra quem está autenticado. Anônimo é redirecionado para o LoginPath
[Authorize(Roles = "Recepcao")]Autenticado e no perfil. Autenticado sem o perfil recebe 403 e cai no acesso negado
[AllowAnonymous]Abre uma action específica dentro de um Controller que está protegido
 
[Authorize(Roles = "Recepcao")]
public class PacientesController : Controller
{
    // as oito actions da Aula 12 seguem protegidas de uma vez
}
Takeaway

No atributo sobre a classe, a regra vale para todas as actions do Controller. Sem nenhum atributo, a action continua pública: no ASP.NET Core, protegido é o que você marcou, não o contrário.

Os perfis e o primeiro usuário, semeados na subida [2]

Perfil é linha na tabela AspNetRoles: se ninguém criar, [Authorize(Roles = "Recepcao")] barra todo mundo. E falta o primeiro usuário, já que a tela de cadastro ficará protegida.

foreach (var perfil in new[] { "Recepcao", "Medico" })
    if (!await roleManager.RoleExistsAsync(perfil))
        await roleManager.CreateAsync(new IdentityRole(perfil));

var email = "recepcao@clinicavida.local";
if (await userManager.FindByEmailAsync(email) is null)
{
    var usuario = new IdentityUser { UserName = email, Email = email };
    var senha = config["SeedRecepcao:Senha"]
        ?? throw new InvalidOperationException("Defina a senha.");
    await userManager.CreateAsync(usuario, senha);
    await userManager.AddToRoleAsync(usuario, "Recepcao");
}

A senha inicial não é escrita no código nem commitada. Ela vem da configuração, hoje guardada pelo user-secrets da sua máquina. Este usuário é didático e local: em produção, o primeiro acesso é criado por outro caminho e trocado logo depois.

O menu mostra só o que aquele usuário alcança

@if (User.Identity is not null && User.Identity.IsAuthenticated)
{
    @if (User.IsInRole("Recepcao"))
    {
        <a asp-controller="Pacientes" asp-action="Index">Pacientes</a>
    }
    <form asp-controller="Conta" asp-action="Logout" method="post">
        <button type="submit">Sair, @User.Identity.Name</button>
    </form>
}
else
{
    <a asp-controller="Conta" asp-action="Login">Entrar</a>
}
Takeaway

Esconder o link é experiência de uso, não é segurança. A URL continua existindo e pode ser digitada. Quem protege de verdade é o [Authorize] no servidor; o menu apenas evita mostrar ao usuário uma porta que ele não abre.

Exercício do Ciclo 2: anotar três actions

Voltando à matriz do Ciclo 1, 8 minutos

  1. Escolha três actions da sua aplicação, uma de cada linha da matriz: pública, da recepção e do médico.
  2. Escreva, para cada uma, o atributo exato que ela deve receber, e diga se ele vai sobre a classe ou sobre a action.
  3. Uma delas precisa ser uma action pública dentro de um Controller protegido: nela use [AllowAnonymous].
  4. Ao lado de cada uma, anote o que o usuário errado vê ao tentar acessar: a tela de login ou o acesso negado.
[Authorize(Roles = "Recepcao")]   // sobre a classe
public class ConsultasController : Controller
{
    [AllowAnonymous]              // sobre a action
    public IActionResult Solicitar() => View();
}

Quiz de fixação

O que o atributo [Authorize] aplicado a um Controller garante?
  • A Que o usuário autenticado tem perfil de administrador, com acesso irrestrito a todas as actions do Controller.
  • B Que a senha do usuário é armazenada de forma criptografada nas tabelas criadas pelo Identity.
  • C Que a aplicação passa a responder somente por HTTPS, recusando qualquer requisição feita em texto puro.
  • D Que somente requisições autenticadas chegam às actions, sendo as demais redirecionadas para a tela de login.
