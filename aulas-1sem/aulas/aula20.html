De onde viemos: a Aula 19 colocou a Clínica Vida+ no ar [3]

Seu entregável da semana passada: a aplicação containerizada com Docker, publicada pelo Codespaces, com URL acessível e registrada no README.md. É dessa URL que sai a demonstração de hoje.

O que ficou pronto no seu fork

  • Dockerfile multi-stage, build no SDK e execução no runtime do ASP.NET.
  • compose.yaml com os serviços web e db, o banco em mysql:8.4.
  • .env no .gitignore, nunca no repositório.
  • Porta encaminhada em modo público no Codespaces.

O que isso mudou na prática

  • A configuração vem do ambiente, com ConnectionStrings__DefaultConnection, e não de arquivo editado à mão.
  • Dentro do compose o host do banco é db, não localhost.
  • Qualquer pessoa com o link abre a sua aplicação, do celular, sem instalar nada.

Um detalhe que decide a nota de hoje: a URL do Codespaces só responde enquanto o codespace está rodando, e ele hiberna por inatividade.

Os sete erros que mais aparecem, e onde olhar primeiro

Nenhum destes é sinal de que você não sabe programar: todos têm um lugar exato para conferir. Guarde esta tela para a reta final do projeto.

O que aparece na tela ou no terminal Onde olhar primeiro
404 ao clicar em um link que existiaO nome do controller e da action. As actions são em inglês: Index, Details, Create, Edit, Delete.
Unable to resolve service for type ClinicaContextFalta o AddDbContext no Program.cs, ou ele foi registrado depois do builder.Build().
Access denied ou Unable to connect to any of the specified MySQL hostsA connection string. Dentro do compose o host é db, e não localhost.
Pending changes ou coluna que não existe no bancoMigration criada e não aplicada. Rode dotnet ef migrations list e depois database update.
A View mostra vazio onde deveria vir o nome do médicoA consulta não pediu o relacionado. Falta Include ou uma projeção com Select.
O formulário volta para a tela sem gravar e sem avisarModelState.IsValid recusou o modelo e a View não exibe o resumo de validação.
Sua URL pública responde 401 ou nem abre para o colegaA porta do Codespaces está privada, ou o codespace hibernou por inatividade.

Revisão dirigida para a prova objetiva, por módulo

A prova objetiva vale 60% da AV1 e cobre os quatro módulos. Abaixo, o que costuma ser cobrado e a confusão que mais derruba questão.

Módulo 1, fundamentos e front-end

Cliente e servidor, DNS, métodos e status HTTP, tags semânticas, seletores e box model, tipos e eventos em JavaScript.
Confusão frequente: achar que GET e POST diferem só no visual. GET pede recurso, POST envia dado que muda estado.

Módulo 2, C# e MVC

Quem faz o quê no MVC, rota padrão, verbos nas actions, Razor, Data Annotations e ModelState.
Confusão frequente: colocar regra de negócio na View. A View exibe; quem decide é o Controller com o Model.

Módulo 3, dados e segurança

Migrations, CRUD, sessão contra cookie, [Authorize] e perfis, verbos e status da API REST, Include e o problema N mais 1.
Confusão frequente: tratar validação do navegador como segurança. O que vale é o que o servidor confere.

Módulo 4, layout e publicação

Layout e Partial Views, grid e componentes do Bootstrap 5, contêiner, imagem e serviço, configuração por variável de ambiente.
Confusão frequente: guardar senha no appsettings.json versionado. Segredo fica fora do repositório.

Antes de apresentar: ligue o codespace [3]

A URL pública da Aula 19 existe enquanto o codespace está rodando, e ele hiberna por inatividade. Isso não é defeito do seu projeto, é como o Codespaces funciona. Na apresentação, porém, o resultado é o mesmo de um projeto fora do ar.

Dez minutos antes da sua vez

  • Abra o codespace do seu fork e espere ele terminar de subir.
  • Suba os serviços com docker compose up -d e aguarde o banco ficar saudável.
  • Confira que a porta está marcada como pública, e não privada.
  • Abra a URL no celular, fora da conta do GitHub, e faça um login de verdade.

Se mesmo assim cair

  • Porta privada devolve 401 para quem não é você. Troque a visibilidade e recarregue.
  • Tenha a aplicação rodando também na sua máquina, na porta que o seu terminal imprimiu, como plano B.
  • Apresentação com URL fora do ar custa nota em funcionalidade e em apresentação.
Takeaway

Ninguém consegue avaliar o que não abre. Ligar o codespace antes é parte da entrega, não um detalhe de operação.

Quiz de fixação

Em uma aplicação ASP.NET Core MVC com EF Core, onde deve ficar a regra que impede agendar duas consultas para o mesmo médico no mesmo horário?
  • A Somente no JavaScript da página de agendamento, que bloqueia o envio do formulário antes de a requisição sair do navegador.
  • B Somente na View, escondendo da lista os horários que já estão ocupados por outra consulta marcada com o mesmo médico.
  • C Somente no banco de dados, com uma restrição de unicidade que rejeita a segunda tentativa de gravar o mesmo horário.
  • D No servidor, na lógica da aplicação e com apoio de restrição no banco, porque a validação feita no navegador pode ser contornada.

Laboratório, passo 3 de 5: dados de demonstração

Um sistema vazio não demonstra nada, e uma lista de "teste 1, teste 2" custa nota em banco de dados e em apresentação.

No banco clinicavida da sua publicação

  1. Garanta 4 especialidades, 3 médicos com CRM válido, 5 pacientes e 8 consultas.
  2. Distribua as consultas entre datas passadas e futuras, para as telas de agenda e histórico terem o que mostrar.
  3. Confirme que nenhuma tela quebra com o banco preenchido: agenda do dia, histórico e relatório por especialidade.
  4. Se o banco de produção estiver vazio, aplique as migrations contra ele antes de semear.
docker compose ps          # o servico db precisa estar healthy antes de aplicar
dotnet ef database update  # com a configuracao de ambiente da Aula 19
# depois, cadastre pelos formulários ou pelo HasData, e confira na tela

Laboratório, passo 4 de 5: tudo integrado na main

A correção clona a main do seu fork. Funcionalidade que ficou numa branch esquecida simplesmente não existe para quem corrige.

No seu fork

  1. Liste as branches e identifique o que ainda não foi integrado.
  2. Integre cada uma na main, resolvendo os conflitos com calma e testando depois de cada integração.
  3. Rode a aplicação a partir da main limpa e repita o teste do passo 1.
  4. Envie tudo para o GitHub e confira pelo navegador que o código está lá.
git branch -a
git checkout main && git pull
git merge feature/deploy      # repita para cada branch que faltar
git push origin main
